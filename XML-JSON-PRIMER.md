# XML and JSON — A Short Primer

> A reference for the two text formats used in [Lab 08 – Complex Parameters](labs/lab08-complex-parameters.md).
> It explains the formats themselves — how a document is built, which rules it must follow, and how to choose between the options each format offers.
> How SQL Server reads and generates XML and JSON is covered in Lab 08, Sections 4 and 6.

Both XML and JSON solve the same problem: describing **structured data as plain text**, so that it can be stored in a file, sent over a network, or passed to a stored procedure.

A comma-separated string such as `1,2,3` can carry a simple list of values. It cannot say *what* each value means, and it cannot describe nesting — an invoice that contains items, for example. XML and JSON can do both.

Throughout this primer we will use the same small piece of data from `AdventureWorksENG`: one invoice with its customer and two line items.

---

## Part 1 – XML

**XML (Extensible Markup Language)** describes data with **tags**. The format does not define any tag names in advance — every document uses its own names, which is what *extensible* means.

### 1.1 Elements

An **element** consists of a start tag, content, and an end tag:

```xml
<FirstName>Ana</FirstName>
```

| Part | Example |
|---|---|
| Start tag | `<FirstName>` |
| Content | `Ana` |
| End tag | `</FirstName>` |

An element can contain text, other elements, or both. Elements inside another element are its **child elements**:

```xml
<Customer>
    <FirstName>Ana</FirstName>
    <LastName>Horvat</LastName>
</Customer>
```

Here `Customer` is the **parent**, and `FirstName` and `LastName` are its **children**.

An element without content can be written as an **empty element**, using a single self-closing tag:

```xml
<Comment></Comment>
<Comment />
```

Both lines mean the same thing.

### 1.2 Attributes

An **attribute** is a name–value pair written inside the start tag:

```xml
<Product ID="776" Color="Black">Mountain-100 Black, 42</Product>
```

This element has two attributes, `ID` and `Color`, and its text content is the product name.

Rules for attributes:

- An attribute value is always written in quotes (`"..."` or `'...'`).
- The same attribute cannot appear twice in one element.
- The order of attributes has no meaning.
- An attribute value is always plain text. It cannot contain other elements.

### 1.3 Well-formed XML

An XML document is **well-formed** if it follows the basic syntax rules. A parser — including SQL Server's `xml` data type — rejects a document that is not well-formed.

| Rule | Correct | Incorrect |
|---|---|---|
| Every element must be closed | `<City>Nin</City>` | `<City>Nin` |
| Elements must be properly nested | `<a><b></b></a>` | `<a><b></a></b>` |
| Names are case-sensitive | `<City></City>` | `<City></city>` |
| Attribute values must be quoted | `ID="1"` | `ID=1` |
| A document has exactly one root element | see below | see below |

The **root element** is the single outermost element that contains everything else.

Not well-formed — two root elements:

```xml
<Customer>Ana</Customer>
<Customer>Marko</Customer>
```

Well-formed — one root element (`Customers`):

```xml
<Customers>
    <Customer>Ana</Customer>
    <Customer>Marko</Customer>
</Customers>
```

> [!NOTE]
> SQL Server's `xml` data type also accepts **XML fragments** — content with more than one top-level element. A standalone XML document, however, must have exactly one root. Using a root element is the safer habit.

### 1.4 Special characters

Some characters have a special meaning in XML and cannot appear directly in text or attribute values. They are written as **entity references**:

| Character | Entity | Why it is special |
|---|---|---|
| `<` | `&lt;` | Starts a tag |
| `&` | `&amp;` | Starts an entity |
| `>` | `&gt;` | Ends a tag (escaping is optional in text, but common) |
| `"` | `&quot;` | Delimits attribute values |
| `'` | `&apos;` | Delimits attribute values |

For example, a comment containing `Price < 100 & in stock` must be written as:

```xml
<Comment>Price &lt; 100 &amp; in stock</Comment>
```

When a longer block of text contains many special characters, it can be wrapped in a **CDATA section**. Everything inside it is treated as plain text:

```xml
<Comment><![CDATA[Price < 100 & in stock]]></Comment>
```

> [!TIP]
> When XML is generated by a tool — for example, `FOR XML PATH` in SQL Server — escaping is done automatically. You usually only need to think about it when writing XML by hand.

### 1.5 Elements or attributes?

The same data can often be written either way:

**Using attributes:**

```xml
<Customer ID="1" FirstName="Ana" LastName="Horvat" />
```

**Using elements:**

```xml
<Customer>
    <ID>1</ID>
    <FirstName>Ana</FirstName>
    <LastName>Horvat</LastName>
</Customer>
```

Both are valid XML and contain the same information. There is no single correct choice, but these guidelines are widely used:

| Use an **attribute** when the value is… | Use an **element** when the value… |
|---|---|
| a simple, single value | can repeat (a customer with several e-mail addresses) |
| an identifier, code, or flag (`ID`, `Type`, `Currency`) | has its own internal structure (an address with street, city, and postal code) |
| *about* the data — metadata | *is* the data itself |
| short | may be long text |
| certain never to need a structure later | may need to be extended later |

A useful test: **could this value ever need its own children, or appear more than once?** If yes, use an element. Attributes cannot be repeated and cannot contain other elements, so changing an attribute into an element later means changing every program that reads the document.

A common, balanced style uses attributes for identifiers and elements for the content:

```xml
<Invoice ID="43659">
    <InvoiceNumber>SO43659</InvoiceNumber>
    <InvoiceDate>2026-11-04</InvoiceDate>
    <Items>
        <Item ProductID="776" Quantity="1" />
        <Item ProductID="777" Quantity="3" />
    </Items>
</Invoice>
```

Notice the `Items` wrapper element. It groups the repeating `Item` elements and makes it obvious where the collection begins and ends.

> [!NOTE]
> Lab 08 uses both styles. Section 4.4 shows how the choice affects the way a value is read: `@Name` for an attribute, `text()` for element text.

### 1.6 Data types in XML

On its own, XML has **no data types**. Everything is text:

```xml
<Quantity>3</Quantity>
<InvoiceDate>2026-11-04</InvoiceDate>
```

To XML, `3` and `2026-11-04` are just characters. The program reading the document decides that the first is a number and the second is a date. In SQL Server, this happens when you specify the target type, as in `.value('...', 'int')`.

Because of this, it is good practice to write values in a standard, culture-independent format:

| Value | Recommended | Avoid |
|---|---|---|
| Date | `2026-11-04` (ISO 8601) | `4.11.2026.` or `11/04/2026` |
| Date and time | `2026-11-04T14:30:00` | `4.11.2026. 14:30` |
| Decimal number | `199.90` | `199,90` |

### 1.7 Comments and the XML declaration

XML documents can contain comments:

```xml
<!-- Prices are without VAT -->
```

A document may also start with an **XML declaration**, which states the XML version and character encoding:

```xml
<?xml version="1.0" encoding="UTF-8"?>
```

The declaration is optional. You will often see it in files exchanged between systems.

### 1.8 Namespaces and schemas (awareness only)

Two more concepts appear in real-world XML. You do not need them for the labs, but you should recognize them.

**Namespaces** prevent name conflicts when one document combines tags from different sources. They look like an attribute starting with `xmlns`:

```xml
<inv:Invoice xmlns:inv="http://example.com/invoice">
    <inv:InvoiceNumber>SO43659</inv:InvoiceNumber>
</inv:Invoice>
```

**XML Schema (XSD)** is a separate document that describes which elements and attributes are allowed, in what order, and with which data types. A document that is well-formed *and* follows its schema is called **valid**. Schemas are common in integrations between organizations, where both sides must agree on an exact structure.

## Part 2 – JSON

**JSON (JavaScript Object Notation)** describes data with **objects** and **arrays**. It started as a subset of JavaScript syntax but is now independent of any programming language. It is the standard format of most web APIs.

### 2.1 Objects

An **object** is a set of **name–value pairs** in curly brackets `{ }`:

```json
{
    "FirstName": "Ana",
    "LastName": "Horvat",
    "Email": "ana.horvat@example.com"
}
```

Each pair is called a **property**. The name and value are separated by a colon, and properties are separated by commas.

Rules for objects:

- Property names are always strings in **double quotes**.
- Names are case-sensitive: `Email` and `email` are different properties.
- The order of properties has no meaning.
- Property names in one object should be unique.

### 2.2 Arrays

An **array** is an ordered list of values in square brackets `[ ]`:

```json
["Red", "Black", "Silver"]
```

Most often, an array contains objects of the same shape:

```json
[
    { "ProductID": 776, "Quantity": 1 },
    { "ProductID": 777, "Quantity": 3 }
]
```

Unlike object properties, array elements **have an order**, and it is preserved.

### 2.3 Data types

Unlike XML, JSON has a small set of built-in types:

| Type | Example | Note |
|---|---|---|
| String | `"Ana"` | Always in double quotes |
| Number | `3`, `199.90`, `-1.5e3` | No quotes; the decimal separator is always `.` |
| Boolean | `true`, `false` | Lowercase, no quotes |
| Null | `null` | Lowercase, no quotes; means "no value" |
| Object | `{ ... }` | |
| Array | `[ ... ]` | |

Note the difference between these values:

```json
{
    "Quantity": 3,
    "ProductNumber": "3",
    "Comment": null
}
```

`3` is a number, `"3"` is a string, and `null` means the value is missing.

> [!IMPORTANT]
> JSON has **no date type**. Dates are written as strings, usually in ISO 8601 format:
>
> ```json
> { "InvoiceDate": "2026-11-04T14:30:00" }
> ```
>
> The program reading the JSON must know that this string represents a date and convert it.

Other types used by databases, such as `money` or `decimal(10,2)`, also have no direct equivalent. They are written as JSON numbers, and the reader decides on the exact type.

### 2.4 Valid JSON

JSON syntax is strict. These are common mistakes:

| Rule | Correct | Incorrect |
|---|---|---|
| Names use double quotes | `"Name": "Ana"` | `Name: "Ana"` or `'Name': 'Ana'` |
| Strings use double quotes | `"Ana"` | `'Ana'` |
| No comma after the last item | `[1, 2, 3]` | `[1, 2, 3,]` |
| No comments | — | `// comment` or `/* comment */` |
| Literals are lowercase | `true`, `null` | `True`, `NULL` |

Inside strings, some characters must be **escaped** with a backslash:

| Character | Written as |
|---|---|
| `"` | `\"` |
| `\` | `\\` |
| New line | `\n` |
| Tab | `\t` |

```json
{ "Comment": "Customer said: \"Deliver after 5 PM.\"" }
```

### 2.5 Objects or arrays?

In JSON, the choice is usually not between two ways of writing a value, but between two **structures**:

| Use an **object** when… | Use an **array** when… |
|---|---|
| you describe **one thing** with named properties | you have **a list of things** |
| each value has a different meaning | all items have the same meaning and shape |
| the order does not matter | the order matters or the number of items varies |

A common mistake is to use numbered property names instead of an array:

**Avoid:**

```json
{
    "Item1": { "ProductID": 776, "Quantity": 1 },
    "Item2": { "ProductID": 777, "Quantity": 3 }
}
```

**Prefer:**

```json
{
    "Items": [
        { "ProductID": 776, "Quantity": 1 },
        { "ProductID": 777, "Quantity": 3 }
    ]
}
```

The second version can contain any number of items, and every program reading it can simply loop through the array.

Another rule of thumb: keep the **types consistent**. If `Quantity` is a number in one item, it should be a number in every item. Mixing `3` and `"3"` makes the data harder to process.

### 2.6 What JSON does not have

Compared with XML, JSON is deliberately simple:

- **No attributes.** Every value is a property, so the "element or attribute?" question does not exist.
- **No comments.**
- **No namespaces.**
- **No built-in schema.** A separate standard, **JSON Schema**, can describe the expected structure, similar to XSD for XML. It is commonly used in API documentation.

## Part 3 – Comparing XML and JSON

### 3.1 The same data in both formats

An invoice with its customer and two line items:

**XML:**

```xml
<Invoice ID="43659">
    <InvoiceNumber>SO43659</InvoiceNumber>
    <InvoiceDate>2026-11-04</InvoiceDate>
    <Customer ID="1">
        <FirstName>Ana</FirstName>
        <LastName>Horvat</LastName>
    </Customer>
    <Comment />
    <Items>
        <Item ProductID="776" Quantity="1" UnitPrice="2024.99" />
        <Item ProductID="777" Quantity="3" UnitPrice="2024.99" />
    </Items>
</Invoice>
```

**JSON:**

```json
{
    "IDInvoice": 43659,
    "InvoiceNumber": "SO43659",
    "InvoiceDate": "2026-11-04",
    "Customer": {
        "IDCustomer": 1,
        "FirstName": "Ana",
        "LastName": "Horvat"
    },
    "Comment": null,
    "Items": [
        { "ProductID": 776, "Quantity": 1, "UnitPrice": 2024.99 },
        { "ProductID": 777, "Quantity": 3, "UnitPrice": 2024.99 }
    ]
}
```

How the parts correspond:

| Concept | XML | JSON |
|---|---|---|
| One entity | element (`<Customer>`) | object (`{ ... }`) |
| A simple value | attribute or child element | property |
| A collection | repeated elements, often in a wrapper (`<Items>`) | array (`[ ... ]`) |
| A missing value | omitted or empty element | `null` or omitted property |
| A number | text — the reader decides the type | number |

Notice that the JSON version is shorter: it has no end tags, and the collection is marked directly with `[ ]`.

### 3.2 Differences at a glance

| | XML | JSON |
|---|---|---|
| Building blocks | elements and attributes | objects, arrays, values |
| Data types | none — everything is text | string, number, boolean, null |
| Dates | text (ISO 8601 recommended) | string (ISO 8601 recommended) |
| Size | larger (start and end tags) | more compact |
| Comments | yes | no |
| Schema | XSD, widely used | JSON Schema, optional |
| Namespaces | yes | no |
| Typical use | document exchange, older and enterprise integrations, SOAP web services, configuration files, office document formats | REST APIs, web and mobile applications, modern configuration files |
| SQL Server support | dedicated `xml` data type | functions over `nvarchar` text (a native `json` type exists in newer versions) |

### 3.3 When to use which

In practice, the choice is usually made **by the system you communicate with**, not by personal preference:

- If data comes from a **web or mobile application**, or a **REST API**, it is almost always JSON.
- If you integrate with an **older enterprise system**, a government service, or a partner that publishes an XSD, it is usually XML.

When you can choose freely:

- Choose **JSON** for simple, data-oriented structures — records and lists of records. It is shorter and easier to read.
- Choose **XML** when you need a strict, formally validated structure, namespaces, or documents that mix text and markup.

> [!NOTE]
> When the client is your own application and the target is SQL Server, a **Table-Valued Parameter** may be a better option than either format. Lab 08, Section 7 compares all the approaches.

1. Why is this not a well-formed XML document: `<Customer>Ana</Customer><Customer>Marko</Customer>`?
2. A product can have several colors. Should `Color` be an attribute or a child element? Why?
3. How do you write the text `Price < 100 & in stock` inside an XML element?
4. What is the difference between `"Quantity": 3` and `"Quantity": "3"` in JSON?
5. Find the errors in this JSON: `{ Name: 'Ana', "Active": True, }`
6. How is a date represented in JSON?
7. Why is an array better than properties named `Item1`, `Item2`, `Item3`?
8. Which XML construct corresponds to a JSON array?

<details>
<summary>Show answers</summary>

1. **Two root elements** — A well-formed document has exactly one root element. Wrapping both in a parent element, such as `<Customers>`, fixes the problem.

2. **A child element** — An attribute cannot appear twice in the same element, so it cannot hold several colors. Repeated values are written as repeated elements, for example `<Colors><Color>Red</Color><Color>Black</Color></Colors>`.

3. **Escape the special characters** — `<Comment>Price &lt; 100 &amp; in stock</Comment>`. Alternatively, use a CDATA section: `<Comment><![CDATA[Price < 100 & in stock]]></Comment>`.

4. **Number vs. string** — `3` is a JSON number, and `"3"` is a string that happens to contain a digit. A program reading the data may treat them differently, so the type should be used consistently.

5. **Four errors** — The property name `Name` is not in double quotes; the string `'Ana'` uses single quotes; `True` must be lowercase `true`; and there is a comma after the last property.

6. **As a string** — JSON has no date type. Dates are written as strings, preferably in ISO 8601 format, such as `"2026-11-04"` or `"2026-11-04T14:30:00"`.

7. **Arrays handle any number of items** — An array can contain any number of items, and a program can process them in a loop. Numbered property names fix the structure in advance and force every reader to know how many properties exist.

8. **Repeated elements** — A collection in XML is a sequence of repeated elements with the same name, usually inside a wrapper element, such as `<Items><Item /><Item /></Items>`.

</details>
